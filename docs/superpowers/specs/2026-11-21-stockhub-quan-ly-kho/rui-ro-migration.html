9. Quản trị Rủi ro Kỹ thuật & Chiến lược Migration

Nhận diện các rủi ro vi phạm 3 quy tắc bất biến, biện pháp phòng vệ đa tầng và quy trình migration cơ sở dữ liệu an toàn.

Nguyên tắc cốt lõi: Không bao giờ dựa vào một tầng phòng vệ duy nhất. Toàn bộ 3 quy tắc bất biến phải được bảo vệ đa tầng: từ Frontend UI $\rightarrow$ Application Validator $\rightarrow$ Domain Model $\rightarrow$ EF Core Interceptor $\rightarrow$ Ràng buộc Database Constraint.

Ma trận Rủi ro & Biện pháp phòng vệ (Risk Matrix)

Mã rủi ro Mô tả rủi ro Mức độ Tác động Giải pháp phòng vệ đa tầng
RSK-01 Tranh chấp đồng thời làm âm tồn kho (Quy tắc 1)
Hai nhân viên cùng xuất 1 mặt hàng cùng thời điểm.		 Cao Kho bị âm, sai lệch tồn thực tế, vi phạm quy tắc cốt lõi. 1. Domain: Kiểm tra Available >= Quantity.
2. EF Core: Khóa lạc quan qua RowVersion.
3. Database: Ràng buộc CHECK (QuantityOnHand >= 0) tại mức schema.
RSK-02 Sửa đổi hoặc xóa phiếu đã duyệt (Quy tắc 2)
Gửi request trực tiếp qua Postman/Curl để sửa phiếu đã duyệt.		 Trung bình Mất tính trung thực chứng từ, sai lệch đối chiếu sổ sách. 1. Validation: FluentValidation chặn ở tầng Handler.
2. Domain: Entity method ném ngoại lệ nếu Status != Draft.
3. EF Interceptor: AuditableInterceptor cấm thay đổi trạng thái nếu gốc là Approved.
RSK-03 Tái sử dụng liên kết duyệt của Kế toán (Quy tắc 3)
Kế toán click duyệt đúp (double-click) hoặc dùng lại link đã duyệt.		 Cao Cộng/trừ kho lặp lại 2 lần, làm sai số lượng tồn kho. 1. Giao dịch DB: Kiểm tra UsedAt == null và gán UsedAt = UtcNow trong cùng 1 transaction.
2. Frontend: Vô hiệu hóa nút duyệt ngay khi submit.
3. API: Trả về 410 Gone ngay lập tức nếu UsedAt != null.
RSK-04 Lộ token phê duyệt qua nhật ký log
Token bí mật bị in vào Serilog/Console dẫn đến bị can thiệp.		 Thấp Người không có thẩm quyền duyệt hộ chứng từ. 1. Che dữ liệu: LoggingBehavior loại trừ trường Token.
2. Lưu DB: Chỉ lưu mã băm SHA-256 của token, không lưu token dạng rõ.

Chiến lược Migration Cơ sở Dữ liệu (EF Core 10)

Áp dụng quy trình chuẩn theo AGENTS.md §9:

  1. Sinh migration có ý nghĩa: Mỗi thay đổi schema là một migration riêng biệt với tên mô tả rõ ràng (VD: dotnet ef migrations add InitialCreate_StockHub -p src/Infrastructure -s src/WebApi).
  2. Kiểm tra mã SQL trước khi áp dụng: Luôn xuất SQL script bằng lệnh dotnet ef migrations script --idempotent để review cấu trúc bảng, khóa ngoại, chỉ mục index và ràng buộc CHECK.
  3. Quy trình Expand & Contract cho các bản cập nhật sau:
    • Giai đoạn 1 (Expand): Thêm cột/bảng mới dưới dạng nullable hoặc có default value. Code mới đọc cột mới hoặc cũ.
    • Giai đoạn 2 (Migrate): Chuyển đổi dữ liệu cũ sang cấu trúc mới.
    • Giai đoạn 3 (Contract): Xóa cột cũ sau khi toàn bộ hệ thống đã ổn định.
  4. Khởi tạo dữ liệu tự động trong Docker (Seed Data): Khi khởi chạy bằng docker compose up --build, tầng WebApi tự động thực hiện await context.Database.MigrateAsync() và nạp dữ liệu mẫu ban đầu (3 tài khoản Admin, Thủ kho, Kế toán; 3 kho hàng; 15 sản phẩm mẫu) để phục vụ chấm bài và quay video tức thì.

Kế hoạch Rollback & Khôi phục khi có sự cố

Rollback Database: Do áp dụng Migration idempotent, khi cần hạ cấp có thể chỉ định chính xác phiên bản mong muốn bằng lệnh dotnet ef database update <TargetMigrationName>.
Môi trường Docker: Khi cần làm sạch toàn bộ dữ liệu để test lại từ đầu: docker compose down -v (xóa volume DB) và docker compose up --build để tự động dựng lại schema và nạp seed data sạch sẽ.
